# Бэкенд и база данных

Расширение цели (2026-09-17): модель решает задачу под ключ через весь стек, фронт плюс бэк плюс БД, работая только локально. Этот документ фиксирует выбор стека бэкенда и причины.

## Из чего исходим

Стек выбирается не «лучший вообще», а лучший для маленькой локальной модели, которая работает агентом в цикле «правка, `npm run verify`, починка»:

1. **Один язык на весь стек.** Ёмкость модели на 4–9B не делится между двумя экосистемами, а типы и схемы переиспользуются.
2. **Расхождение слоёв должно ловиться проверкой.** Главный риск сквозной задачи: поле добавили в таблицу, но забыли в API или форме. Чем больше таких ошибок превращается в ошибку `tsc` или упавший тест, тем больше модель чинит сама.
3. **Ноль инфраструктуры.** Никаких сервисов, Docker и портов для проверки: и на ноутбуке пользователя, и в грейдере бенчмарка, где каждая рабочая копия получает свою БД.
4. **Быстрый verify.** Каждая лишняя секунда проверки умножается на число ходов агента.
5. **Мало файлов и мало магии.** Декораторы, DI-контейнеры, кодогенерация и отдельные языки схем удлиняют траектории и добавляют шагов, где можно ошибиться.
6. **Распространённость.** Чем больше библиотеки в предобучении, тем меньше приходится учить с нуля.

## Решение

| Слой | Выбор | Версия на 2026-09-17 |
|---|---|---|
| Язык и рантайм | TypeScript, Node 22 LTS | как в шаблоне |
| HTTP-фреймворк | Hono, `@hono/node-server` | 4.13.8, 2.1.1 |
| Валидация | zod 4, `@hono/zod-validator` | 4.6.5, 0.9.1 |
| БД | SQLite через `better-sqlite3` | 13.0.3 |
| ORM и миграции | Drizzle ORM, drizzle-kit | 0.45.2, 0.31.10 |
| Тесты | Vitest, запросы через `app.request()` без сети | как в шаблоне |
| Контракт фронт-бэк | REST, общие zod-схемы в `shared/` | |

### Почему Hono

- Крошечный API на веб-стандартах `Request`/`Response`; маршрут это функция, без декораторов и модулей.
- `app.request('/api/tasks')` исполняет запрос в процессе: тесты бэкенда не поднимают сервер и не занимают порт.
- 48,7 млн скачиваний в неделю, второе место после Express (97,8 млн), впереди Fastify (9,5) и NestJS (10,5).
- Отвергнуто: **Express 5** лучше всех знаком моделям, но без типов и валидации из коробки, тестам нужен supertest; **Fastify 5** хорош, но система плагинов и JSON Schema это лишние понятия; **NestJS 12** даёт 5–7 файлов на сущность с декораторами и DI, что удлиняет траектории вдвое; **Elysia** привязана к Bun и мало распространена.

### Почему SQLite и Drizzle

- SQLite это файл для разработки и `:memory:` для тестов: БД создаётся за миллисекунды на каждый тест-файл, сервисов нет.
- Drizzle описывает таблицы обычным TypeScript, типы строк выводятся без кодогенерации. Запросы близки к SQL, который модель знает хорошо.
- drizzle-kit генерирует SQL-миграции из изменения схемы одной неинтерактивной командой (ограничение: переименование колонок вызывает интерактивный вопрос, поэтому правило шаблона «колонки не переименовываем, добавляем новые»).
- Отвергнуто: **Prisma** это отдельный язык схемы и шаг генерации клиента, два лишних места для ошибки; **Kysely** требует описывать типы таблиц вручную или кодогенерацией; **сырой SQL** без типов не ловит расхождения компилятором.
- Запасной путь на Postgres: **PGlite** (Postgres в процессе через WASM, 12,4 млн скачиваний в неделю) поддерживается тем же Drizzle. Диалект схемы другой (`pgTable` вместо `sqliteTable`), запуск экземпляра около секунды. Переход возможен, но модель учится одному диалекту, поэтому решить нужно до генерации датасета.

### Контракт между фронтом и бэком

Общие zod-схемы в `shared/` это единственный источник правды о форме данных:

- бэкенд валидирует вход через `zValidator` теми же схемами, которыми фронт валидирует форму;
- фронт типизирует RTK Query через `z.infer` от них же;
- тип строки Drizzle сверяется со схемой на уровне типов (`satisfies`), так что расхождение таблицы и контракта это ошибка `tsc`.

Отвергнуто: **Hono RPC** и **tRPC** дают сквозные типы, но требуют особого стиля описания маршрутов и непривычной связки с RTK Query; **OpenAPI с кодогенерацией** добавляет шаг генерации.

### Моки исчезают

Сейчас фронтовые тесты ходят в MSW-обработчики с отдельной in-memory «базой», то есть логика API написана дважды. С настоящим бэкендом MSW остаётся только мостом: `http.all('/api/*', ({ request }) => app.fetch(request))` с SQLite в памяти. Тесты фронта идут против настоящего кода API. Слой моков как место для ошибок пропадает, а расхождение URL или формы ответа ловится тестом.

## Раскладка проекта

Один пакет, без монорепозитория: одна команда `npm run verify`, один `node_modules`, существующие пути фронта и 76 задач бенчмарка не ломаются.

```
src/            фронт, как сейчас (алиас @/)
server/         бэкенд (алиас @server/)
  app.ts        сборка маршрутов
  features/<name>/routes.ts, routes.test.ts
  db/schema.ts, client.ts, migrate.ts, seed.ts
  index.ts      запуск на порту 3000
shared/         контракт (алиас @shared/): zod-схемы и типы по сущностям
drizzle/        SQL-миграции
```

`tsconfig` разделён на фронт и сервер, оба видят `shared/`. В разработке Vite проксирует `/api` на Hono. `npm run verify` остаётся одной командой: typecheck обоих проектов, lint, format, тесты фронта и бэка.

## Что такое задача под ключ

Новая сущность проходит путь: схема в `shared/` → таблица и миграция → маршруты с валидацией и кодами ошибок → тесты API → эндпоинты RTK Query → форма, список, страница, маршрут, навигация → тесты фронта. Это 12–15 файлов, поэтому поэтапная работа с verify после каждого этапа становится обязательной.

Навыки бэкенда, которым учит датасет: CRUD с единым форматом ошибок (400 с перечнем проблем, 404, 409), связи и внешние ключи, каскады, фильтры, сортировка и пагинация в SQL, транзакции, уникальные ограничения, агрегирующие эндпоинты, миграции и сиды, починка расхождений между слоями.

За рамками первой итерации: аутентификация, загрузка файлов, вебсокеты, фоновые задачи, деплой.

## Открытые вопросы к владельцу

1. **SQLite или Postgres.** Рекомендация SQLite: проще, быстрее verify, ноль инфраструктуры. Если реальные проекты живут на Postgres, берём PGlite и диалект `pg` сразу.
2. **Аутентификация.** Если нужна в задачах под ключ, добавляется второй итерацией (сессия в cookie, защита маршрутов, страница входа).
