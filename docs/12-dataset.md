# Датасет

Шаг 7 плана. Код в `bench/src/dataset/`, данные в `bench/dataset/` (не в git, кроме захваченного запроса).

## Главное решение: учитель работает в той же обвязке

Reference показал, что DeepSeek V4 Pro через Pi решает задачи бенчмарка короткими чистыми траекториями: медиана 7 ходов, read → edit → verify, почти без ошибок инструментов. Это и есть образцовые обучающие примеры, уже в точном формате ученика. Поэтому генератор датасета это тот же прогон, что и бенчмарк:

1. Пул задач, не пересекающийся с бенчмарком.
2. Учитель (DeepSeek через Pi, конфигурация как у `base-harness`) решает каждую задачу в свежей копии шаблона.
3. В датасет попадают только прогоны, где `npm run verify` зелёный и есть изменённые файлы; при наличии скрытых тестов они тоже должны пройти.
4. Транскрипт конвертируется в обучающий пример.

Что это даёт:

- Формат данных совпадает с форматом работы буквально: тот же системный промпт, те же схемы инструментов, тот же AGENTS.md.
- Учитель не пишет код «из головы», а работает в реальном шаблоне, поэтому tsc отсеивает незнание новых версий библиотек.
- Лицензионная серая зона с условиями Anthropic исчезает: учитель DeepSeek.

## Формат примера

`bench/dataset/student-request.json` это захваченный запрос, который Pi отправляет модели ученика: системный промпт (с AGENTS.md шаблона), схемы четырёх инструментов, параметры. Конвертер `convert.ts` берёт `agent_end.messages` из транскрипта и собирает:

```
{ "messages": [system, user, assistant(+tool_calls), tool, ..., assistant], "tools": [...], "meta": {...} }
```

Это OpenAI-совместимый формат чата с вызовами инструментов, который понимает chat template Qwen3.5 и Unsloth.

## Чему учим, по типам провалов базы

| Провал базы | Что должен показывать пример |
|---|---|
| Пустая генерация после чтения | Каждая траектория заканчивается правкой, verify и коротким отчётом |
| Неверный формат вызова инструмента | Только валидные вызовы; траектории с ошибками инструментов исключаются или обрезаются |
| Абсолютные пути, `cd`, работа во /tmp | Относительные пути, cwd это проект; траектории с абсолютными путями отфильтровываются |
| bash вместо read/edit | Чтение через `read`, точечные правки через `edit`; `write` только для новых файлов |
| Нет самопроверки | Последний вызов инструмента всегда `npm run verify`, и он зелёный |
| Стена контекста | Ограничение длины: не больше 15–20 ходов на пример |
| Частичная работа | Прошедший verify означает, что все слои затронуты и типы сходятся |

## Цикл исправления

Самое важное поведение в датасете: запустить проверку, увидеть красное, прочитать вывод, починить, запустить снова, закончить только на зелёном. Отдельной инструкцией не задаётся, задаётся отбором траекторий.

- Каждая траектория заканчивается зелёным `npm run verify` как последним вызовом инструмента, затем короткий отчёт. Прогоны, где учитель отчитался без проверки, отбрасываются даже при верном решении.
- Целевая доля траекторий с циклом «красный verify → правка → зелёный verify»: не меньше трети. Иначе модель выучит проверку как формальность и не увидит, как читать вывод tsc и тестов.
- Если учитель редко ошибается с первой попытки, ошибки провоцируются задачами пула: подложенные баги, изменения схемы, от которых гарантированно падают старые тесты, ужесточённые правила линтера.
- Хвост после зелёного verify обрезается: траектория заканчивается на зелёной проверке и отчёте.

Метрики для сравнения базы и файнтюна: «закончила на зелёном verify» и «починила после красного». Разница между ними показывает, выучен ли цикл.

## Фильтры при отборе

- `grade.solved` или как минимум verify зелёный плюс непустой diff.
- Ноль ошибок инструментов (или обрезка траектории до первой ошибки, если после неё всё исправлено; решить по данным).
- Нет абсолютных путей и `cd` в вызовах.
- Не больше N ходов.
- Финальное сообщение короткое и описывает сделанное.
- Последний вызов инструмента это зелёный verify (см. «Цикл исправления»).

## Пул задач

Таксономия: слой × тип работы × предметная область × сложность × формулировка. Слои те же, что в бенчмарке, включая `config`. Скаффолд с нуля в датасет не входит: его делает шаблон. Целевой объём первой волны: 300–500 траекторий после фильтров, то есть 500–800 прогонов учителя.

### Как гарантируется разноплановость

1. **Покрытие по сетке.** У каждой клетки таксономии квота, генератор заполняет клетки и печатает матрицу покрытия. Пустые клетки видны сразу.
2. **Разнообразие формулировок.** На клетку несколько шаблонов промпта и словарь вариаций (поля, подписи, условия), плюс перефразирование сильной моделью. Дубликаты отбрасываются по нормализованному сходству текстов.
   **Язык.** Целевой пользователь почти всегда пишет по-русски, поэтому датасет в основном русский: целевая доля 70%, не 100%, чтобы не отвязать поведение от английского окружения (код, ошибки компилятора, документация) и не просадить английский незаметно. Пул: три русские формулировки на каждую задачу (`paraphrase.ts pool/tasks 3 ru`), текст задачи русский, подписи в кавычках, пути, эндпоинты и сообщения английские. Пропорция задаётся при отборе (`select.ts ... 0.7`): русские берутся все, английские досэмплируются. Учитель отвечает на языке промпта, так что финальный отчёт в русских траекториях русский. Код, комментарии и AGENTS.md остаются английскими.
3. **Разнообразие предметных областей на всех уровнях.** Варианты шаблона через оверлеи: контакты, проекты, заказы, заметки добавляются в проект до запуска учителя, чтобы простые задачи существовали не только про сущность «задачи». Эталоны контактов и проектов уже есть в бенчмарке.
4. **Разнообразие затронутого кода.** После прогона учителя считаются наборы изменённых файлов; квоты на набор, перекос отбрасывается.
5. **Качество траектории.** Автоматически: verify и фильтры формы. Выборочно: модель-судья сравнивает результат с промптом. Вручную: эксперт по стеку смотрит случайные 20–30 траекторий на вопрос «написал бы так сам».

Непересечение с бенчмарком: по тексту и по набору затронутых файлов, чтобы задача бенчмарка не просочилась в обучение в перефразированном виде.

### Объём

Для LoRA на узкое поведение хватает сотен и первых тысяч траекторий: одна траектория это 8–15 ходов ассистента, каждый со своим обучающим сигналом. Первая волна 300–500, вторая до 1–2 тысяч, если замер показывает рост. Десятки тысяч нужны для широких навыков или полного дообучения, здесь они дадут запоминание шаблона, а не навык.

## Открытые вопросы

- Reasoning-трассы: Unsloth советует не меньше 75% примеров с рассуждением, чтобы сохранить thinking у Qwen3.5. Решается по итогам замера base-harness-thinking: если thinking не помогает, учим и запускаем без него.
- Нужны ли скрытые тесты для задач пула или достаточно verify + непустой diff + выборочная проверка судьёй.
- Соотношение коротких (1–3 хода) и длинных (10–20 ходов) траекторий.

## Инструменты

- `bench/src/dataset/pool.ts` генерирует пул в `bench/pool/tasks` (не в git): 250 промптов на 2026-09-14, 19 шаблонов × вариации × три сущности (задачи из шаблона, контакты и проекты через оверлеи эталонов бенчмарка), 8 подложенных багов со структурными проверками, дедупликация против бенчмарка (порог 0,5) и внутри области (0,8 с маскированием имён сущности), матрица покрытия в выводе.
- `bench/src/dataset/paraphrase.ts` расширяет пул перефразировками через DeepSeek: те же ограничения, другая подача (баг-репорт, запрос продакта, короткий тикет). Нужен `DEEPSEEK_API_KEY`.
- Прогон учителя это обычный `run` с `BENCH_TASKS_DIR=bench/pool/tasks` и конфигурацией `reference-deepseek`. Для задач пула действует правило: рабочая копия без изменений никогда не считается решённой.
- `bench/src/dataset/convert.ts` собирает обучающие примеры из решённых прогонов.
- `bench/src/dataset/select.ts` применяет правила отбора: решено и есть изменения; последний вызов инструмента зелёный verify, хвост после него обрезается, финальный отчёт сохраняется; ни одной неудачной правки; ни `cd`, ни `/tmp`, ни путей вне рабочей копии; 2–20 ходов. Красный verify внутри траектории разрешён, это цикл исправления. Ошибки `grep`/`find` без совпадений считаются безобидными. Абсолютные пути внутри рабочей копии переписываются в относительные, машинные пути в системном промпте заменяются на нейтральный `/workspace`. Печатает отчёт: сколько оставлено, почему отброшено, доля траекторий с циклом исправления.

Команды:

```bash
cd bench
node src/dataset/pool.ts                                   # сгенерировать пул
DEEPSEEK_API_KEY=... node src/dataset/paraphrase.ts pool/tasks 2   # +2 перефразировки на задачу
BENCH_TASKS_DIR=$PWD/pool/tasks DEEPSEEK_API_KEY=... node src/cli.ts run --run-id teacher-v1 --configs reference-deepseek --tasks all --reps 1
node src/dataset/select.ts teacher-v1 dataset/train.jsonl 0.7  # отбор с отчётом, 70% русских
```

Ночная цепочка (`overnight.sh` плюс `results/night-chain.log`): английский пул → русская волна пула → русские варианты бенчмарка → перезапуск учителя на русских задачах. Всё возобновляемое.

## Версии датасета

Не «побольше того же», а ответ на вопрос замера. Ориентир: две-три версии.

1. `train-v1`: дисциплина инструментов и цикл исправления, 300–500 траекторий, 70% русских. Первое измерение: сколько даёт SFT вообще.
2. `train-v2`: реакция на замер v1. Провал на сквозных задачах → больше длинных траекторий; просадка на русском → больше русского; дисциплина есть, но не знает API новых версий → задачи, где это критично.
3. `train-v3`, если дойдём: другой формат, а не объём: отрицательные примеры или обучение с наградой от verify на траекториях самой дообученной модели.

## Ревью качества, 2026-09-15

Десять случайных решённых задач учителя просмотрены как на код-ревью (4 английских, 3 перефразированных, 3 русских). Вердикт: рабочий код по конвенциям проекта, уровень крепкого мидла с проблесками сеньора. Годится в обучение с поправками.

Сильное: минимальные правки, паттерны проекта соблюдены (`Controller`, `aria-invalid`, `FieldError`, `@/`, токены, инвалидация тегов); числовое поле с конвертацией и четырьмя тестами; правильное разведение input/output типов zod в `useForm`; агент не поверил выдуманному пути в промпте и нашёл настоящий файл; русские задачи решаются так же чисто, отчёт на русском.

Слабое: тесты на новое поведение отсутствуют в 4 из 10 (по всем решённым: тесты трогают 37%, новый тест-файл добавляют 11%); поиск с `placeholder`/`aria-label` вместо видимой подписи через `Field`; `disabled` чекбокс как индикатор в таблице; Redux-слайс ради одной подсветки; раздутые отчёты с заголовками.

Дефекты данных, не учителя: шаблон обязательного поля противоречил сам себе («required» и «данные без него продолжают работать»); перефразирование в 4 случаях из 1200 выдумало пути файлов.

Что изменено: в шаблоны пула добавлены явные «покрой тестом» для задач с новым поведением; перефразировки с несуществующими путями отбрасываются; в отборе финальный отчёт обрезается до первого абзаца (не длиннее 600 символов), цветовые коды терминала вычищаются, `cd` в корень рабочей копии не дисквалифицирует траекторию, а вырезается (это вернуло 75 примеров). Отбор на 501 прогоне: оставлено 385, из них 43% с циклом исправления.

## Инцидент с пулом, 2026-09-15

Генератор пула начинал с удаления `pool/tasks`; запуск ради проверки новых шаблонов стёр 1200 перефразировок, пока учитель работал по ним. Решённые траектории не пострадали: их промпты лежат в транскриптах, а конвертер читает промпт оттуда. Оригиналы восстановлены детерминированно с теми же идентификаторами (проверено на 85 решённых), перефразировки запрошены заново. Генератор теперь append-only: существующие папки не трогает, промпты пула считает дубликатами, новые шаблоны пишутся с новым префиксом волны (`POOL_PREFIX=Q`).

## Первые данные

- 32 удачные траектории DeepSeek на задачах бенчмарка сконвертированы как проверка конвертера. В обучение они не идут: это отложенная выборка.
- Пилот учителя на пуле (2026-09-14, `teacher-pilot`, каждая двенадцатая задача): все прогоны решены, отбор оставляет около 70% (отброшены `cd` и упавшая цепочка команд), 40% оставленных содержат цикл исправления. Форма траекторий: `bash(read) → read → edit → bash(verify)`, иногда `edit → verify → edit → verify`. Это подтверждает, что учитель в той же обвязке даёт нужные данные без ручного вмешательства.

## Пул под ключ, 2026-09-17

`bench/src/dataset/pool-fs.ts` генерирует задачи для фулстек-шаблона в `bench/pool-fs/tasks` (не в git), префикс `FS`. 78 заданий в восьми семействах:

| Семейство | Сколько | Ступень | Что |
|---|---|---|---|
| entity | 24 | 3 | 12 сущностей под ключ, каждая в двух подачах: спецификация и запрос продакта |
| child | 4 | 3 | дочерние сущности задач с внешним ключом и каскадом: комментарии, подзадачи, ссылки, учёт времени |
| field | 10 | 2 | поле через весь стек на задачах (кроме `dueDate`: это задача бенчмарка) |
| api | 12 | 1–2 | только сервер: фильтры и сортировка в SQL, агрегаты, уникальный индекс, транзакция, действия |
| web | 12 | 1–2 | только интерфейс поверх настоящего API |
| fix | 6 | 2 | подложенные баги в разных слоях; тест, который ловил баг, из заготовки удаляется |
| test | 6 | 2 | написать тесты |
| config | 4 | 2 | скрипты, окружение, логирование |

Сущности пула (клиенты, товары, заказы, заметки, теги, статьи, события, расходы, автомобили, переговорные, рецепты, обращения) не пересекаются с зарезервированными сущностями бенчмарка; генератор это проверяет.

**Русский без учителя.** У каждого задания есть русская формулировка, написанная вручную (`pool-fs-ru.ts`): генератор пишет пару `FS0001-…` и `FS0001-…-ru` с одинаковыми проверками и заготовкой. Итого 156 задач без единого обращения к DeepSeek. Перефразировщик для русского берёт источником именно русский текст (с русского на русский выходит естественнее, чем перевод), понимает пути `server/` и `shared/` и сверяет их с нужным шаблоном.

Остальное готово и ждёт разрешения на расходы: `convert.ts` подставляет системный промпт по шаблону задачи (`dataset/student-request-fullstack.json`), `select.ts` нормализует пути контейнера, `bench/teacher-fs.sh` гоняет учителя только вне пиковых часов тарифа и останавливается на ошибке провайдера. Прогон теперь сохраняет изменённые файлы в `<результат>/changed`: из решённых сущностей получится вторая волна задач ступени 2 (фильтр, правка, связь) уже на них, как F03/F04/F07 в бенчмарке.

План волн: A) 156 задач плюс перефразировки; B) задачи ступени 2 поверх решённых сущностей из волны A; C) после первого обучения: собственные попытки модели, проверенные грейдером.
