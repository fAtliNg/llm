# Бенчмарк

Код в `bench/`. Задачи в `bench/tasks/`, прогон через Pi в JSON-режиме, результаты в `bench/results/`.

## Зачем

1. Ответить на вопрос эксперимента: повышает ли файнтюн долю задач стека, проходящих проверки.
2. Отделить эффект обучения от эффекта обвязки: четыре конфигурации гоняются на одних задачах.
3. Показать, где именно модель ломается: по слою, типу работы, ступени сложности, причине провала.
4. Не обмануть себя: задачи фиксируются до датасета и в него не попадают.

## Оси разнообразия

Бенчмарк покрывает целевое распределение, а не «максимально разные» задачи. Всё внутри стека, на простых предметных областях.

| Ось | Значения |
|---|---|
| Слой | component, form, query, routing, test, mock, config (настройка проекта: зависимости, инструменты, конфиги), cross (сквозная через все слои) |
| Тип работы | create, modify, fix, test, refactor |
| Сложность | 1 один файл, 2 несколько файлов в одной фиче, 3 новая фича через все слои |
| Формулировка | spec (точное ТЗ с именами) или product (как сказал бы пользователь) |

Продуктовые формулировки проверяют рассуждение: модель сама решает, какие слои затронуть. Спецификационные отделяют «не смогла придумать» от «не смогла написать». Градиент обязателен: если все задачи требуют планирования, 9B провалит всё, и диагностики не будет.

Целевое распределение: сквозные и правки существующего кода треть, формы и запросы по пятой части, остальное поровну. Предметные области: задачи (в шаблоне), контакты, заказы, проекты.

## Что требуется от вайбкодинга

- Исследование проекта: часть задач не называет файлы, модель должна найти место сама.
- Цикл исправления: часть задач почти наверняка не проходит с первой попытки, модель должна прочитать ошибку и починить.
- Метрики агентного поведения: запустила ли модель проверку сама, число ходов, число неверных вызовов инструментов.

## Формат задачи

```
bench/tasks/<id>/
  task.json      id, title, layer, work, difficulty, formulation, tags, testGlob
  prompt.md      текст задачи, как его получит модель
  setup/         (опционально) файлы поверх шаблона до запуска: подложенные баги
  hidden/        скрытые тесты, копируются в src/__bench__/ после работы модели
  solution/      эталонное решение поверх шаблона, для проверки самой задачи
  mutants/<n>/   (опционально) мутации кода; тесты, написанные моделью, обязаны их поймать
  checks.json    (опционально) структурные проверки: файл существует, счётчик вхождений
```

Задача считается решённой, если прошли все четыре стадии `npm run verify`, скрытые тесты, структурные проверки и все мутанты пойманы. Каждая стадия пишется отдельно, чтобы видеть причину провала.

## Прогон

Для каждой конфигурации, задачи и повторения:

1. Рабочая копия шаблона в `bench/.work/`, `node_modules` через симлинк.
2. Наложить `setup/`.
3. Запустить Pi: `pi --mode json --model <model> --thinking <level> <флаги конфигурации> "<prompt>"` с cwd в рабочей копии и таймаутом. Поток событий сохраняется как транскрипт.
4. `npm run verify` по стадиям.
5. Скопировать `hidden/`, прогнать только их.
6. Структурные проверки и мутанты.
7. Записать `result.json` с метриками и причинами.

Конфигурации в `bench/configs/`: модель, thinking, включены ли AGENTS.md и skills. Четыре основные: база и файнтюн, каждая без обвязки и с ней. Плюс `reference` с сильной облачной моделью для проверки задач.

## Переоценка после правки задачи

Если скрытый тест или проверка задачи изменились после прогонов, `regrade --run-id <id> [--tasks ...]` пересчитывает оценку на сохранённых рабочих копиях, без повторного запуска модели. Пример: тест T07 создавал контакт «Ada Lovelace», а сильная модель засеяла моки тем же именем. Тест переписан на имя, которого не может быть в сидах, и прогоны переоценены.

## Возобновление и остановка

Прогон именуется через `--run-id`. Готовые тройки (конфигурация, задача, повторение) пропускаются, поэтому остановленный прогон продолжается той же командой, а `--reps 3` после `--reps 1` добавляет только недостающие повторения. Остановка по SIGINT или SIGTERM убивает текущего агента, готовые результаты остаются.

## Диагностика каждого прогона

Рядом с `result.json` пишется `analysis.md`: результат и причина, время, ходы, инструменты, форма траектории вида `bash(read)×12 → read → edit → bash(verify)`, самые частые ошибки инструментов, изменённые файлы и автоматические наблюдения. Наблюдения это эвристики под датасет: чтение файлов через bash вместо `read`, неудачные правки, абсолютные пути, работа во `/tmp`, повторы команд, отсутствие или избыток проверок, долгая разведка до первой правки, блуждание после последней правки, разросшийся контекст, файлы эталонного решения, которых модель не коснулась. Всё это попадает в отчёт в раздел «Observations per run».

## Метрики

| Метрика | Что показывает |
|---|---|
| solved | главный результат, все проверки прошли |
| typecheck, lint, format, tests | стадии verify по отдельности |
| hidden | скрытые тесты |
| toolCalls по типам, toolErrors | работа в агенте |
| ranVerify | модель сама запустила проверку до финального ответа |
| turns, tokens, wallSeconds | эффективность; в отчёте время на каждую задачу, медиана и сумма по конфигурации |
| firstEditAt, lastEditAt, verifyRuns, shape | разведка до правки, блуждание после, самопроверка, форма траектории |
| failureReason | формат, неприменившаяся правка, не сошлось после ошибки, неверная логика, таймаут |

## Контроли валидности

Числам можно верить только после трёх проверок самого бенчмарка:

1. `validate`: эталонное решение проходит все проверки задачи. Иначе задача нерешаема.
2. `null`: пустой прогон без изменений проваливает задачу. Иначе проверки проходят сами по себе.
3. `reference`: сильная модель решает большинство задач. Если нет, задачи сформулированы плохо, чинить до экспериментов с обучением.

## Воспроизводимость и проверка результатов

- Генерация недетерминирована: каждая задача гоняется несколько раз, в отчёте среднее и разброс. Разница между конфигурациями значима, только если больше разброса.
- Каждый прогон сохраняет рабочую копию, транскрипт, вывод всех стадий и `result.json`. Любое число в отчёте сводится к папке, где можно руками запустить `npm run verify` и прочитать, что делала модель.
- `report` собирает таблицу конфигурация × слой × сложность из всех `result.json`.

## Thinking как конфигурация

Вопрос «учить с рассуждением или без» решается замером: база с thinking и без на продуктовых формулировках. Если рассуждение поднимает результат больше, чем стоит по скорости, датасет генерируется с короткими reasoning-трассами.

## Метрики формы траектории

В отчёте (`### Trajectory shape`) кроме доли решённых считаются признаки, которые меняются раньше, чем доля решённых:

- вызовов инструментов до первой правки: сколько агент читает, прежде чем что-то сделать;
- вызовов после последнего зелёного `npm run verify`: доделывает ли он после успешной проверки или останавливается;
- доля траекторий, заканчивающихся зелёным verify;
- доля траекторий с красной проверкой и доля тех, где после красной была зелёная той же категории или полный verify (цикл исправления);
- доля траекторий без единой правки.

Первый замер, 2026-09-15 (11 задач для базы, 48 для reference):

| | до первой правки | после зелёного verify | заканчивает зелёным verify | чинит после красного | без правок |
|---|---|---|---|---|---|
| base-bare | 12,3 | - | 0% | - | 27% |
| base-harness | 7,6 | 10,7 | 3% | - | 14% |
| base-harness-thinking | 7,0 | 5,0 | 0% | 3 из 3 | 9% |
| reference DeepSeek | 7,0 | 0,1 | 79% | 14 из 14 | 0% |

База читает столько же, сколько DeepSeek, но после зелёного verify делает ещё десять вызовов, а на зелёном verify не заканчивает почти никогда. Именно это должно измениться после обучения раньше, чем доля решённых.

## Бенчмарк v2: задачи под ключ, 2026-09-17

Версия 1 (76 задач, шаблон `template/`) заморожена: на ней сняты все прежние цифры. Версия 2 измеряет новую цель: задача через весь стек на незнакомой сущности. Шаблон `template-fullstack/`, стек в `14-backend.md`.

Что поменялось в стенде:

- У задачи появилось поле `template`: `frontend` (по умолчанию) или `fullstack`. Рабочая копия, базовая линия диагностики и системный промпт при конвертации выбираются по нему.
- Скрытые тесты двух видов: `hidden/` кладутся в `src/__bench__` (веб, jsdom, идут через мост MSW в настоящий Hono с БД в памяти), `hidden-api/` кладутся в `server/__bench__` (node, `app.request`). Результаты суммируются.
- Проверка типа `command` для структурных условий, которые не выразить grep: например, «появилась новая миграция».
- Сущности бенчмарка зарезервированы: `invoice`, `employee`, `booking`, `contact`, `project`. Генератор пула падает, если слово встретилось в промпте. Модель видит их впервые на замере.

Все задачи проходят `validate` (эталон решает) и `null` (без изменений не решается). DeepSeek решил F01 в контейнере за 28 ходов, 6 из 6 скрытых тестов.

Ловушка стека, найденная при написании F07: `drizzle-kit` для SQLite при добавлении колонки через `ALTER TABLE` теряет `ON DELETE SET NULL`. Схема говорит одно, миграция делает другое, удаление руководителя падает на внешнем ключе. Эталон очищает подчинённых явно в транзакции. Скрытые тесты проверяют поведение, а не механизм.

### Попытки и частичный балл

Цель сформулирована как «не меньше 90% задач ступеней 2–3 решено с трёх попыток», поэтому отчёт группирует повторы (`--reps 3`) по задаче: решено в среднем за попытку, решено хотя бы в одной, решено во всех. Рядом частичный балл: доля пройденных скрытых тестов. Он двигается раньше, чем доля решённых. Пример на старых данных: база 9B на ступени 3 решила 0 из 6, но прошла 67% скрытых тестов; v1.1 на ступенях 2–3 решила те же 35%, что и база, при 80% скрытых тестов против 54%. Отдельная таблица делит результат по версиям бенчмарка.
