# Локальная установка

Что нужно на M2 Pro для прогона бенчмарка и ручной работы с моделью.

## Node и npm

```bash
nvm install 22.23.2 && nvm use 22.23.2
```

Устанавливать зависимости через npm 11: `npx npm@latest install`. npm 10 падает на этом наборе peer-зависимостей.

## Ollama и модель

Ollama уже установлен (`/usr/local/bin/ollama`, версия 0.32.9 на 2026-09-14). Модель:

```bash
ollama pull qwen3.5:9b
```

Тег `9b` это Q4_K_M, около 6,6 ГБ. Контекст задаётся явно, иначе Ollama тихо обрежет его до 4k и tool calling развалится:

```bash
ollama create qwen3.5:9b-32k -f bench/ollama/Modelfile
```

KV-кэш в Q8 и прочие настройки сервера через переменные окружения при запуске `ollama serve`: `OLLAMA_KV_CACHE_TYPE=q8_0`, `OLLAMA_FLASH_ATTENTION=1`.

Проверить, что модель отвечает и поддерживает инструменты:

```bash
curl -s http://localhost:11434/api/chat -d '{"model":"qwen3.5:9b-32k","messages":[{"role":"user","content":"What is the weather in Paris?"}],"tools":[{"type":"function","function":{"name":"get_weather","parameters":{"type":"object","properties":{"city":{"type":"string"}}}}}],"stream":false,"think":false}' | head -c 600
```

В ответе должен быть `tool_calls` с `get_weather`.

## Pi

Pi установлен локальной зависимостью в `bench/`, глобально ставить не нужно. Конфигурация провайдера лежит в репозитории: `bench/pi-home/models.json`. Запуск через обёртку:

```bash
cd bench && npm run pi -- --list-models
```

Ручная сессия с моделью в шаблоне:

```bash
cd bench && npm run pi -- --model ollama/qwen3.5:9b-32k --thinking off -c ../template
```

## Результаты первого запуска (2026-09-14, M2 Pro 16 ГБ)

1. Tool calls в формате Pi корректные: `read`, `edit` с `oldText`/`newText`, `bash`. Правки применяются.
2. Thinking выключается: Ollama принимает `reasoning_effort: "none"`, Pi маппит `--thinking off` на него через `thinkingLevelMap` в `bench/pi-home/models.json`. Reasoning-токенов в ответах ноль.
3. Скорость 9B Q4 на M2 Pro: генерация 27 токенов/с, чтение контекста около 280 токенов/с (замер 2026-09-17 на промптах 5–10k токенов, `num_thread 4`). Первый замер 21,5 и 180 был на коротком промпте, который занижает чтение. Для сравнения Qwen3.5-2B в Q8 на том же Mac: 63 и около 1350. При замере на нескольких запросах подряд учитывать кэш префикса: повторный запрос с тем же началом читает только хвост.
4. Память: модель целиком на GPU при контексте 32768 (`ollama ps` показывает 100% GPU, 6,5 ГБ).
5. T00 (переименовать кнопку) решён с обвязкой за 12 минут и 92 хода: 81 вызов bash, 5 read, 2 edit, 16 ошибок инструментов, контекст дорос до 24k. Модель предпочитает `cat`, `grep` и `sed` через bash вместо `read` и `edit`, придумывает пути, пишет во временные файлы, но в итоге делает правильную правку и сама запускает `npm run verify`.

## Ключи для облачных конфигураций

Ключи не хранятся в репозитории. Прогон читает их из переменных окружения терминала, из которого запущен:

- `DEEPSEEK_API_KEY` для `reference-deepseek` (основной reference и учитель датасета).
- `GEMINI_API_KEY` для `reference-gemini`: бесплатный тариф, 5 запросов в минуту, прогон сам поднимает троттлинг-прокси.
- `ANTHROPIC_API_KEY` для `reference`. Вход через подписку Claude в Pi возможен (`/login`), но сторонние приложения расходуют «дополнительное использование», а не лимиты подписки.

Всё, что Pi пишет в `bench/pi-home` кроме двух конфигов (`auth.json`, `models-store.json`, `bin/`, сессии), игнорируется git.

## Цены DeepSeek и время суток

У DeepSeek тариф зависит от времени: в будни с 04:00 до 07:00 и с 09:00 до 13:00 по Москве цены вдвое выше, остальное время и выходные вдвое дешевле. V4 Pro вне пика: ввод 0,66 $/M, попадание в кэш 0,022 $/M, вывод 1,98 $/M. Реальная цена задачи учителя 1,5–2 цента вне пика, вдвое больше в пик. Большие прогоны ставить после 13:00 или на ночь.

Встроенная таблица цен Pi для DeepSeek устарела и занижает расход в 3–4 раза: оценки стоимости из транскриптов считать по реальному тарифу с учётом пика, а не по полю `cost` в usage.

## Стенд на арендованном GPU-сервере

Тот же сервер, что для обучения (RTX PRO 6000, Ubuntu 24.04), после обучения служит стендом для бенчмарка: Ollama, Node 22, копия репозитория через `rsync` без `node_modules`, `npm ci` в `template/` и `bench/`. Проверка одной задачи там занимает 15 секунд против минуты на Mac.

Настройки, без которых стенд работает плохо:

- `OLLAMA_NUM_PARALLEL` не меньше числа одновременных агентов, иначе запросы стоят в очереди по 15 секунд при работе в полсекунды. Задаётся через `systemctl edit ollama` (override с `Environment=`), плюс `OLLAMA_KEEP_ALIVE=24h` и `OLLAMA_MAX_LOADED_MODELS=2`, чтобы база и файнтюн жили в памяти одновременно.
- `PARAMETER num_thread 4` в Modelfile: llama.cpp крутит по одному занятому потоку на ядро, пока считает GPU, и на 16 ядрах съедает 9 из них, из-за чего проверки кода в параллельных копиях голодают (load average 20). С ограничением нагрузка падает вдвое, карта становится узким местом, как и должно быть.
- Таймаут задачи 10 минут вместо 30: на быстром железе этого хватает модели, которая идёт по делу.
- `--parallel 4` на прогон; два прогона (база и файнтюн) одновременно дают 8 агентов и полную загрузку карты по вычислениям при 15 ГБ памяти из 96.

Результаты сервера лежат под своими идентификаторами (`base-server-v1`, `ft-server-v1`) и не смешиваются с прогонами на Mac.

## Безопасность прогонов

Агент под тестом получает `bash` без песочницы. 9B за десятки часов ни разу не вышла за рабочую копию, но это свойство модели, а не стенда:

- 2026-09-17 базовая Qwen3.5-2B на первой же задаче искала файлы по `/Users/sergey/Desktop/Projects` и пробовала `curl` на выдуманный адрес.
- В тот же день базовая Qwen3.5-4B на третьей задаче выполнила `rm -rf "<bench>/.work/base4b-mac-v1"`, то есть стёрла папку всего прогона уровнем выше своей задачи. Пострадали только одноразовые рабочие копии.

Правило: новые, маленькие и базовые модели гоняются только на одноразовом сервере или в контейнере, где удалять нечего. `bench/tools/guard.py` следит за вызовами и останавливает прогон при выходе из рабочей копии задачи, сетевых и привилегированных командах и разрушительных командах с абсолютными путями. Он срабатывает после исполнения команды и годится как сигнализация внутри песочницы, но не вместо неё.

### Песочница для прогонов на личной машине

`bench/docker/Dockerfile` собирает образ `llm-bench`: Node 22, копии `template/` и `bench/` без результатов, пула, датасета, моделей и `.env.local`. Агент работает пользователем `node`; шаблон и код бенчмарка принадлежат root и доступны ему только на чтение, писать можно в `.work`, `results` и `pi-home`. С хоста монтируется одна папка результатов текущего прогона. Ollama остаётся на хосте ради GPU, контейнер ходит к ней на `host.docker.internal:11434`.

```bash
docker build -f bench/docker/Dockerfile -t llm-bench .          # из корня репозитория
R=base4b-docker-v1; mkdir -p bench/results/$R
docker run -d --name bench-4b --restart on-failure:5 -v "$PWD/bench/results/$R:/work/llm/bench/results/$R" \
  llm-bench node src/cli.ts run --run-id $R --configs base4b-mac --tasks all --reps 1
docker logs -f bench-4b            # ход прогона
docker rm -f bench-4b              # остановить; повторный run с тем же run-id продолжит
```

Образ это снимок: задачи, шаблоны и код стенда копируются в него при сборке. После добавления задач (бенчмарк v2 вырос до 24 задач 2026-09-17) или правок стенда образ нужно пересобрать той же командой `docker build`, иначе контейнер гоняет старый набор. Прогон бенчмарка v2 с тремя попытками, как требует целевой показатель:

```bash
R=base4b-v2; mkdir -p bench/results/$R
docker run -d --name bench-v2 --restart on-failure:5 -v "$PWD/bench/results/$R:/work/llm/bench/results/$R" \
  llm-bench sh -c "rm -f results/$R/.lock; exec node src/cli.ts run --run-id $R --configs base4b-mac --tasks tag:v2 --reps 3"
node bench/src/cli.ts report --run-id $R      # таблицы «Attempts and partial score» и «Safety»
```

Память: по умолчанию Docker Desktop берёт под виртуальную машину 8 ГБ. На Mac с 16 ГБ вместе с моделью в Ollama это уводит систему в подкачку, интерфейс подвисает. Контейнеру хватает 4 ГБ: `memoryMiB` в `~/Library/Group Containers/group.com.docker/settings.json`, затем перезапуск Docker Desktop.

Кэш промптов движка: llama.cpp по умолчанию держит в оперативной памяти до 8 ГБ состояний прошлых промптов (`--cache-ram 8192`), Ollama этот флаг не задаёт. При работе агента кэш заполняется, и процесс `llama-server` с моделью на 3,4 ГБ разрастается до 13 ГБ; на 16 ГБ система уходит в подкачку. Лечится переменной окружения, которую движок читает сам: закрыть приложение Ollama и запустить сервер вручную

```bash
LLAMA_ARG_CACHE_RAM=512 OLLAMA_KEEP_ALIVE=24h /Applications/Ollama.app/Contents/Resources/ollama serve
```

В логе должно появиться `prompt cache is enabled, size limit: 512 MiB`. После этого процесс держится около 5,7 ГБ. Вернуть как было: остановить этот процесс и открыть приложение Ollama.

Проверено 2026-09-17: из контейнера не видно `/Users`, удалить шаблон агент не может, проверка задач проходит. Худшее, что может сделать модель, это стереть результаты собственного прогона, поэтому рядом каждые десять минут делается копия в `<run>.backup`. ## ПК с RTX 4070 Super как стенд, 2026-09-18

Windows 11, WSL2 Ubuntu 24.04, доступ с Mac по `ssh -p 2222 user@192.168.0.18` (проброс порта в Windows; после включения ПК нужно открыть Ubuntu и `sudo service ssh start`). Внутри WSL: Ollama (ставится официальным скриптом, видит карту через CUDA), Docker CE как песочница для модели под тестом, Node 22 через nvm, копия репозитория в `~/llm` (rsync с Mac, не git). Настройка одним скриптом `pc-setup.sh` под sudo (Docker, Ollama, override `OLLAMA_HOST=0.0.0.0`, `OLLAMA_NUM_PARALLEL=3`, `OLLAMA_KEEP_ALIVE=24h`).

Особенности:
- Docker Hub из России не отвечает: базовый образ `node:22-bookworm-slim` для amd64 вытянут на Mac (`docker pull --platform linux/amd64`), передан `docker save | docker load`, дальше сборка `llm-bench` на ПК идёт без Docker Hub (npm доступен).
- Контейнер запускается с `--network host --add-host host.docker.internal:127.0.0.1`: образ переписывает адрес Ollama на `host.docker.internal`, а в сети хоста это имя само не резолвится.
- Скорости: 4B Q4 около 50 токенов/с в одиночку, 9B Q4 около 73; чтение контекста около 290 токенов/с. Это в 2,5–3 раза быстрее M2 Pro. Три агента параллельно дают около 1,5× общего темпа; загрузка карты скачет 0–85%, потому что агенты ждут инструменты.
- Обученные модели кладутся в `~/llm/models/<версия>/` и регистрируются в Ollama через Modelfile с `RENDERER qwen3.5`, `PARSER qwen3.5` и параметрами сэмплирования как на сервере.

Прогон бенчмарка v2 на ПК: `docker run -d --name bench-4b --restart on-failure:5 --network host --add-host host.docker.internal:127.0.0.1 -v "$PWD/bench/results/$R:/work/llm/bench/results/$R" -v "$PWD/bench/configs:/work/llm/bench/configs:ro" llm-bench sh -c "rm -f results/$R/.lock; exec node src/cli.ts run --run-id $R --configs base4b-mac --tasks tag:v2 --reps 3 --parallel 3"`. Возобновляемый: `docker rm -f bench-4b` останавливает, та же команда продолжает.

## Аренда 4090 48 ГБ на сутки, 2026-09-18

Провайдер с посуточной оплатой: RTX 4090 48 ГБ, 16 ядер, 32 ГБ, 2 055 ₽/сутки (в 3,5 раза дешевле Selectel по часам). Ubuntu 24.04 с CUDA, доступ по ключу через `ssh-copy-id` (провайдер даёт пароль root; пароль в руках владельца, я ключ только использую). Подготовка: `train/sync-to-server.sh root@HOST` (репозиторий, датасет, скрипты, пилотные задачи пула), `bootstrap-server.sh` (venv с torch cu128 и Unsloth, Ollama, Node, npm ci; около 10 минут), затем `session-v2.sh`.

`session-v2.sh` рассчитан на работу без присмотра: чекпоинты обучения каждые 25 шагов с возобновлением, cron-сторож каждые 10 минут перезапускает сценарий, а тот пропускает сделанное (готовый GGUF, идущий или завершённый бенчмарк по `.done`-меткам). Очередь: обучение 4B → бенчмарк v2 (3 попытки) → обучение 9B → бенчмарк 9B (1 попытка, диагностическая точка) → обученная 4B на 218 задачах пула (собственные попытки для второго круга) → базовые 4B и 9B на быстрой карте → Qwen3.5-35B-A3B на пилотных задачах как кандидат в локальные учителя.

Две ямы, найденные при первом запуске: дочерний процесс бенчмарка наследовал дескриптор блокировки `flock`, и после перезапуска сценарий считал себя уже запущенным (лечится `9>&-` у дочерних процессов); проверка «модель уже обучена» искала GGUF не в той папке и запускала обучение заново (лечится `find`). Оба исправлены в скрипте.

Обучение 4B на v2: 628 примеров (18 длиннее 32k отброшены), 158 шагов, 36–56 с/шаг, 2 часа, 20 ГБ памяти. Экспорт Q4_K_M 2,8 ГБ.
