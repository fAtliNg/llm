# Локальная установка

Что нужно на M2 Pro для прогона бенчмарка и ручной работы с моделью.

## Node и npm

```bash
nvm install 22.23.2 && nvm use 22.23.2
```

Устанавливать зависимости через npm 11: `npx npm@latest install`. npm 10 падает на этом наборе peer-зависимостей.

## Ollama и модель

Ollama уже установлен (`/usr/local/bin/ollama`, версия 0.32.9 на 2026-09-14). Модель:

```bash
ollama pull qwen3.5:9b
```

Тег `9b` это Q4_K_M, около 6,6 ГБ. Контекст задаётся явно, иначе Ollama тихо обрежет его до 4k и tool calling развалится:

```bash
ollama create qwen3.5:9b-32k -f bench/ollama/Modelfile
```

KV-кэш в Q8 и прочие настройки сервера через переменные окружения при запуске `ollama serve`: `OLLAMA_KV_CACHE_TYPE=q8_0`, `OLLAMA_FLASH_ATTENTION=1`.

Проверить, что модель отвечает и поддерживает инструменты:

```bash
curl -s http://localhost:11434/api/chat -d '{"model":"qwen3.5:9b-32k","messages":[{"role":"user","content":"What is the weather in Paris?"}],"tools":[{"type":"function","function":{"name":"get_weather","parameters":{"type":"object","properties":{"city":{"type":"string"}}}}}],"stream":false,"think":false}' | head -c 600
```

В ответе должен быть `tool_calls` с `get_weather`.

## Pi

Pi установлен локальной зависимостью в `bench/`, глобально ставить не нужно. Конфигурация провайдера лежит в репозитории: `bench/pi-home/models.json`. Запуск через обёртку:

```bash
cd bench && npm run pi -- --list-models
```

Ручная сессия с моделью в шаблоне:

```bash
cd bench && npm run pi -- --model ollama/qwen3.5:9b-32k --thinking off -c ../template
```

## Результаты первого запуска (2026-09-14, M2 Pro 16 ГБ)

1. Tool calls в формате Pi корректные: `read`, `edit` с `oldText`/`newText`, `bash`. Правки применяются.
2. Thinking выключается: Ollama принимает `reasoning_effort: "none"`, Pi маппит `--thinking off` на него через `thinkingLevelMap` в `bench/pi-home/models.json`. Reasoning-токенов в ответах ноль.
3. Скорость: генерация 21,5 токенов/с, prefill 180 токенов/с на коротком контексте.
4. Память: модель целиком на GPU при контексте 32768 (`ollama ps` показывает 100% GPU, 6,5 ГБ).
5. T00 (переименовать кнопку) решён с обвязкой за 12 минут и 92 хода: 81 вызов bash, 5 read, 2 edit, 16 ошибок инструментов, контекст дорос до 24k. Модель предпочитает `cat`, `grep` и `sed` через bash вместо `read` и `edit`, придумывает пути, пишет во временные файлы, но в итоге делает правильную правку и сама запускает `npm run verify`.

## Ключи для облачных конфигураций

Ключи не хранятся в репозитории. Прогон читает их из переменных окружения терминала, из которого запущен:

- `DEEPSEEK_API_KEY` для `reference-deepseek` (основной reference и учитель датасета).
- `GEMINI_API_KEY` для `reference-gemini`: бесплатный тариф, 5 запросов в минуту, прогон сам поднимает троттлинг-прокси.
- `ANTHROPIC_API_KEY` для `reference`. Вход через подписку Claude в Pi возможен (`/login`), но сторонние приложения расходуют «дополнительное использование», а не лимиты подписки.

Всё, что Pi пишет в `bench/pi-home` кроме двух конфигов (`auth.json`, `models-store.json`, `bin/`, сессии), игнорируется git.

## Цены DeepSeek и время суток

У DeepSeek тариф зависит от времени: в будни с 04:00 до 07:00 и с 09:00 до 13:00 по Москве цены вдвое выше, остальное время и выходные вдвое дешевле. V4 Pro вне пика: ввод 0,66 $/M, попадание в кэш 0,022 $/M, вывод 1,98 $/M. Реальная цена задачи учителя 1,5–2 цента вне пика, вдвое больше в пик. Большие прогоны ставить после 13:00 или на ночь.

Встроенная таблица цен Pi для DeepSeek устарела и занижает расход в 3–4 раза: оценки стоимости из транскриптов считать по реальному тарифу с учётом пика, а не по полю `cost` в usage.

## Долгие прогоны

```bash
caffeinate -i -s -w <pid>    # не давать Mac уснуть, пока жив процесс прогона
kill <pid>                   # остановить: агент убивается, готовые задачи остаются
```

Повторный запуск с тем же `--run-id` продолжает с места остановки. Один и тот же `--run-id` нельзя запустить дважды: второй процесс откажется стартовать.


## Стенд на арендованном GPU-сервере

Тот же сервер, что для обучения (RTX PRO 6000, Ubuntu 24.04), после обучения служит стендом для бенчмарка: Ollama, Node 22, копия репозитория через `rsync` без `node_modules`, `npm ci` в `template/` и `bench/`. Проверка одной задачи там занимает 15 секунд против минуты на Mac.

Настройки, без которых стенд работает плохо:

- `OLLAMA_NUM_PARALLEL` не меньше числа одновременных агентов, иначе запросы стоят в очереди по 15 секунд при работе в полсекунды. Задаётся через `systemctl edit ollama` (override с `Environment=`), плюс `OLLAMA_KEEP_ALIVE=24h` и `OLLAMA_MAX_LOADED_MODELS=2`, чтобы база и файнтюн жили в памяти одновременно.
- `PARAMETER num_thread 4` в Modelfile: llama.cpp крутит по одному занятому потоку на ядро, пока считает GPU, и на 16 ядрах съедает 9 из них, из-за чего проверки кода в параллельных копиях голодают (load average 20). С ограничением нагрузка падает вдвое, карта становится узким местом, как и должно быть.
- Таймаут задачи 10 минут вместо 30: на быстром железе этого хватает модели, которая идёт по делу.
- `--parallel 4` на прогон; два прогона (база и файнтюн) одновременно дают 8 агентов и полную загрузку карты по вычислениям при 15 ГБ памяти из 96.

Результаты сервера лежат под своими идентификаторами (`base-server-v1`, `ft-server-v1`) и не смешиваются с прогонами на Mac.
