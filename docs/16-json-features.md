# Функционал из JSON: конструктор, которым пользуется модель

Статус: проектная документация, 2026-09-21. Ничего не реализовано. Предложение владельца от 2026-09-20: универсальный механизм, который по JSON строит формы на фронте и запросы на бэкенде, чтобы модель писала JSON, а не код.

## Зачем

Маленькая модель проигрывает задачи не на понимании, а на объёме однотипного кода. Данные за два круга обучения (`bench/reports/fullstack-cycles-1-2-2026-09-19.md`) и замер на ПК: ступень 3 у 4B 0 из 18, из неудач 60% таймауты, 50–55 ходов, 25–30% правок мимо. Обучение на примерах это не лечит (уроки 10–11 в `15-story.md`).

Первая проверка рычага «инструмент вместо данных» уже есть: генератор сущностей (`template-fullstack/scripts/gen-entity.ts`, стенд v2.1). Без дообучения та же 4B решила F02-employees-ru за 14 ходов и 1,2 минуты со скрытыми 9/9, тогда как без генератора эта задача ни разу не решалась за 15 минут. Остальные попытки пробы показали новую границу: модель либо не доверяет генератору и дописывает руками, либо ломается на следующем шаге (вторая миграция, drizzle-kit). Механизм из JSON продолжает эту линию: не одноразовый генератор, а описание, которое остаётся источником правды и покрывает доработки, а не только создание сущности.

## Принцип

1. **Описание сущности — единственный источник правды.** `entities/<plural>.json` описывает поля, правила, список, фильтры, связи и действия. Всё, что можно вывести из описания, выводится механизмом. Модель правит JSON и перезапускает генерацию, а не правит семь файлов.
2. **Граница: данные и структура в JSON, поведение в TypeScript.** Правило, которое нельзя выразить парой строк JSON, пишется как маленькая типизированная функция-хук в одном предсказуемом файле. JSON не должен превращаться в самодельный язык программирования: у него нет условий, циклов и выражений.
3. **Выход механизма — обычный код на нашем стеке.** Никакого движка во время работы: сгенерированные файлы читаются, отлаживаются и тестируются как написанные вручную. Это же снимает риск «модель не знает движок»: она видит обычный Hono, Drizzle, RTK Query.
4. **Регенерация безопасна.** Механизм владеет своими файлами и перезаписывает их; файлы с ручным кодом (хуки, кастомный UI, ручные тесты) не трогает. Граница видна по именам, а не по маркерам внутри файла.

Итог: на девяти задачах из двенадцати описание закрывает 70–100% работы; на всех двенадцати остаток кода — одна-две функции по 10–20 строк в известном файле. Ступень 3 в основном становится ступенью «JSON плюс один хук». Пул из 643 учебных задач раскладывается так же: семейства entity, field, filter, search, sort, edit, boolfilter, fix-column, fix-delete — в JSON; conflict, stats, child, fix-cache — хуки.

## Что описывает JSON

Словарь ниже — цель, а не спецификация первой версии. Первая версия — то, что уже есть в `gen-entity.ts`, плюс пункты, помеченные «этап 1».

**Сущность:** `singular`, `plural`, `label` для навигации, `fields`, `list`, `form`, `filters`, `search`, `actions`, `seeds`.

**Поле:** `name`, `label`, `kind` (text, email, textarea, enum, bool, int, money, date, timestamp, ref), `optional`, `default`, `unique` с текстом 409, `pattern` с текстом ошибки (этап 1), `min`/`max`, `readonly` — поле есть в контракте и таблице, но не в форме и не принимается в POST/PATCH (этап 1; F08 status, F10 favorite, F11 cancelledAt), `ref` — ссылка на другую сущность с `onDelete: setNull | restrict` и текстами 400/409 (этап 2; F07, F09).

**Список:** `columns` с форматом ячейки (text, date с «—», money `$1,250.00`, badge по enum, ссылка по ref, шаблон вида `{startHour}:00–{endHour}:00`), `sort` (этап 1), `paginate` (этап 2), `rowActions` (edit, delete с подтверждением, действия из `actions`).

**Форма:** create и edit (этап 1), сообщения валидации, показ 409 под полем, `submitLabel`.

**Фильтры и поиск:** `filters` по enum-полю с текстом 400 (этап 1; F03), `search` по текстовым полям в SQL без учёта регистра (этап 2; F10).

**Действия:** `actions: [{ name: "send", from: "draft", to: "sent", conflict: "Invoice is not in the right state", button: "Send" }]` — переходы состояния readonly-enum-поля с кнопкой в строке (этап 2; F08, F11). Действие с побочным эффектом за пределами смены статуса — хук.

Что в JSON не попадает никогда: условия и вычисления, запросы к другим таблицам, любые формулировки «если … то …». Всё это хуки.

## Что остаётся кодом: хуки

Один файл на сущность, `server/features/<plural>/rules.ts`, создаётся генератором пустым с типизированными заглушками, дальше механизм его не перезаписывает. Интерфейс узкий и одинаковый для всех сущностей:

- `validate(input, current?) → FieldError | null` — кросс-полевые правила, вызывается в API и, через контракт, в форме (F05 «End must be after start», F07 «cannot manage themselves»).
- `beforeCreate / beforeUpdate(db, next) → Conflict | null` — проверки по базе (F05 пересечение, F11 с учётом отменённых).
- `beforeDelete(db, row) → Conflict | null` (F08 оплаченный счёт).
- `listQuery(db, base) → query` — дополнительная сортировка или вычисляемые колонки (F09 `taskCount`, F10 «избранные первыми», если не выражено в JSON).
- `afterAction(name, db, row)` — побочные эффекты действий.

На клиенте: `src/features/<plural>/custom/` — кастомные ячейки и блоки (F08 строка Outstanding, F10 кнопка избранного), которые список подключает по имени из JSON (`cell: "custom:FavoriteToggle"`).

Ошибка хука должна доходить до формы тем же путём, что и 409 от уникальности: механизм уже умеет показывать сообщение API под полем или над формой.

## Как это работает технически

Два варианта, рекомендация — второй.

1. **Интерпретатор во время работы.** Общие компоненты `EntityList`, `EntityForm` и общий роутер читают JSON и обслуживают любую сущность без кода. Плюс: нет генерации и регенерации. Минусы: движок надо написать и отладить один раз на все случаи; модель, которой нужно выйти за рамки, должна понимать движок; тесты сущности становятся тестами движка; ошибка в JSON проявляется в рантайме, а не в `tsc`.
2. **Повторяемая генерация** (продолжение `gen-entity.ts`). Механизм пишет обычные файлы; повторный запуск перезаписывает свои файлы и не трогает ручные. Плюс: код остаётся кодом на стеке, `tsc` и `verify` ловят несоответствия, модель дописывает знакомые вещи. Минус: нужна дисциплина «свои/чужие файлы» и миграции при изменении полей.

Ключевые детали второго варианта:

- **Свои файлы механизма:** контракт, таблица в схеме, роуты, api, форма, список, страницы, сгенерированные тесты, миграции. **Ручные:** `rules.ts`, `custom/`, любые тесты с суффиксом `.custom.test.ts`. Список «своих» файлов лежит рядом с описанием (`entities/<plural>.lock.json`), чтобы регенерация знала, что перезаписывать, и предупредила, если модель правила «свой» файл руками.
- **Изменение полей → миграция.** Drizzle умеет сравнить схему и сгенерировать миграцию; механизм вызывает это сам, как сейчас. Переименование и удаление полей — отдельный риск (потеря данных), для первой версии запрещено: поле можно только добавить.
- **Сгенерированные тесты** проверяют то, что описано в JSON (400, 404, 409, колонки, форма). Тесты хуков пишет модель, механизм даёт заготовку рядом с `rules.ts`.
- **Валидация описания** — zod-схема как сейчас, ошибки понятным текстом. Это самая дешёвая линия обороны: 4B хорошо чинит JSON по сообщению, плохо — TypeScript по стеку ошибок.

## Как модель этим пользуется

Рабочий цикл, который ложится в `AGENTS.md` и в обучающие примеры:

1. Прочитать задачу, написать или изменить `entities/<plural>.json`.
2. `npm run gen:entity -- entities/<plural>.json` — до зелёного (ошибки описания чинятся в JSON).
3. `npm run verify`.
4. Если в задаче есть правило, которого нет в JSON — реализовать его в `rules.ts` или `custom/`, добавить тест, `verify`.
5. Итог.

Проба 2026-09-20 показала, что именно здесь нужны обучающие примеры: модель должна доверять шагу 2 и не переписывать сгенерированное. Примеры «задача → JSON → generate → verify» короткие (10–20 ходов), их правильность проверяется автоматически, и большую часть можно собирать без учителя: описание известно из генератора пула задач, траекторию можно синтезировать. Учитель нужен только на шаг 4 (хуки), и то не всегда.

## Как измеряем

- Это новая версия стенда (v3). Как и с v2.1: прежние цифры на тегах, сравнение только внутри версии. Перемер: база 4B, v2, DeepSeek на v3.
- Ожидание, которое стоит записать заранее: без дообучения 4B на v3 решает ступень 2 заметно лучше (F01, F03, F04, F12 становятся описанием), на ступени 3 — F02 и, возможно, F10; F05, F07, F08, F09 требуют хука и без обучения скорее не решатся. Если после дообучения на коротких примерах ступень 3 не сдвигается — проблема в хуках, и это уже нормальная задача «написать 15 строк по спецификации», которую 4B решает много лучше, чем «написать 300 строк».
- Метрики поверх обычных: доля попыток, где модель вызвала генератор; доля, где после генератора она правила сгенерированные файлы руками (плохой знак); ходов до первого зелёного `verify`.

## Риски и открытые вопросы

- **Потолок выразительности.** Соблазн добавлять в JSON «ещё одно ключевое слово» на каждую задачу. Правило: новое ключевое слово только если оно нужно трём и более семействам задач пула, иначе хук.
- **Тесты бенчмарка написаны под ручную реализацию.** Скрытые тесты проверяют поведение через HTTP и DOM, не структуру, поэтому должны проходить; но проверки структуры (`checks.json`, «есть миграция», «контракт в `shared/<entity>.ts`») нужно перечитать на совместимость с выходом механизма.
- **Существующие тесты при регенерации.** Если генератор переписывает свои тесты, ручные правки в них теряются; отсюда правило про `.custom.test.ts`.
- **Второй запуск в одном проекте.** Уже поймано на v2.1: правки общих файлов (схема, роутер, навигация) должны сливаться, а не вставляться заново. При регенерации то же самое для удаления: если сущность удалена из `entities/`, механизм в первой версии её не удаляет.
- **Честность KPI.** «Задачи под ключ на узком стеке» с конструктором в стеке — это другой стек, чем был при постановке. Решение владельца: конструктор — часть продукта, KPI считается на нём. Зафиксировать в `04-decisions.md` при старте реализации.
- **Куда девать `tasks`.** Каноническая сущность шаблона написана руками. Либо переписать её как сгенерированную (тогда модель видит один стиль), либо оставить как «пример ручного кода». Склоняюсь к первому: один стиль важнее.

## Этапы, когда решим делать

1. Зафиксировать словарь первой версии (этап 1 из списка выше) и правила «свои/ручные файлы». Один документ, без кода.
2. Регенерация поверх текущего `gen-entity.ts`: lock-файл, перезапись своих файлов, `rules.ts` с заглушками, добавление поля с миграцией.
3. Этап 1 словаря: `pattern`, `readonly`, `sort`, фильтры по enum, форма edit, delete с подтверждением.
4. Прогон DeepSeek и базы на v3, чтобы понять, что механизм закрывает без обучения.
5. Этап 2 словаря: `ref`, поиск, пагинация, действия.
6. Синтетические примеры «задача → JSON → generate → verify», дообучение, замер на ПК.
