# Идея проекта

## Суть

Люди вайбкодят с помощью облачных моделей (Claude, GPT, Cursor). Хочется дать возможность вайбкодить фронтенд с помощью локальной модели, которая работает без интернета, без оплаты токенов и не отправляет код наружу.

Для этого:

1. Взять открытую модель для кода размером около 8B параметров.
2. Собрать датасет под конкретный фронтенд-стек (React + TypeScript + RTK Query + обвязка).
3. Дообучить модель на этом датасете (LoRA).
4. Сравнить качество базовой и дообученной модели на задачах этого стека.

## Гипотеза

Дообучение 8B модели на узком, верифицированном датасете под конкретный стек с фиксированными версиями библиотек заметно повышает качество генерации кода в этом стеке по сравнению с базовой моделью.

Измеримая формулировка: SFT на данных стека повышает долю задач, проходящих тесты, на отложенном бенчмарке этого стека, и при этом превосходит дешёвую альтернативу (базовая модель + системный промпт + документация в контексте).

## Что дообучение реально может дать

- Меньше галлюцинаций API. Модель перестаёт выдумывать несуществующие хуки и опции, не путает версии библиотек и похожие библиотеки (RTK Query vs React Query).
- Соблюдение конвенций проекта: структура папок, стиль компонентов, выбранный стейт-менеджер, способ фетчинга. Стабильность ответов от запроса к запросу.
- Более короткие и точные ответы без лишних объяснений.

## Чего дообучение почти наверняка не даст

- React модель уже знает. Выигрыш не от «научить React», а от «научить именно эту связку библиотек этих версий в этом стиле».
- Планирование и многошаговое рассуждение не улучшатся. Это главное узкое место 8B в вайбкодинге: разбить задачу на файлы, прочитать ошибку компилятора, исправить нужное место.
- Агентский цикл (вызовы инструментов, правки в нескольких файлах, реакция на вывод tsc) не улучшится от обучения на парах «задача → код». Для этого нужны траектории агента, что на порядок сложнее собрать.

## Реалистичная планка

Не «замена облака», а «локальный помощник, который в своём стеке стабильно и в едином стиле пишет компоненты, слайсы RTK Query, формы и тесты».

Где результат достижим:

- Генерация в пределах одного файла или компонента по чёткому описанию.
- Работа внутри подготовленного шаблона проекта, где структура и конвенции уже заданы.
- Автодополнение и точечные правки.

Где разрыв с облаком непреодолим на 8B:

- Задачи на 5–8 файлов с планированием.
- Длинные агентские сессии с десятками вызовов инструментов.
- Скорость: около 20 токенов/с на M2 Pro, агентская сессия с большим контекстом растягивается на десятки минут.

## Аргументы за то, что делать стоит

1. Датасет и бенчмарк это актив, который переживёт модель. Выйдет новая 8B база, дообучаем её тем же датасетом за вечер, гоняем тот же бенчмарк. Разрыв с облаком сокращается, работа накапливается.
2. Быстро узнаем, что именно работает. Возможно, половину эффекта даёт не файнтюн, а шаблон проекта плюс документация в контексте. Это тоже результат.

## Продукт: веса или связка?

Рабочая гипотеза: продукт это не сами веса, а связка «веса + шаблон проекта + правильно настроенный агент». Обвязка может дать не меньше, чем обучение. Поэтому эксперимент строится как сравнение четырёх вариантов:

| | Без обвязки | С обвязкой (шаблон + промпт + доки) |
|---|---|---|
| Базовая модель | A | B |
| Дообученная модель | C | D |

Целевая аудитория: разработчики с NDA на код, с плохим интернетом, или не желающие платить за подписку.
